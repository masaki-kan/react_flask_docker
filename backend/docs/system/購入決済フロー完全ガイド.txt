1. 概要
================================================================================

購入フローは、ユーザーが交換する商品を持っていない場合に、金額を提案して商品を
購入できる機能です。エスクロー方式を採用し、買い手の保護を実現しています。

### 主要機能:
- 金額の提案と合意
- Stripe決済（テスト環境）
- エスクロー方式（受取確認まで資金を保管）
- 発送・受取確認
- アーカイブ処理（完了後のデータ保存と削除）

### 関係者:
- Seller: 商品を出品した人（交換を受ける側）
- Buyer: 商品を購入したい人（交換を申請した側）

3. ステータス遷移
================================================================================

### ステータス一覧:

1. pending          - 交換申請中（まだ購入モードではない）
2. price_proposed   - 金額提案中
3. price_agreed     - 金額合意済み
4. paid             - 決済完了
5. shipped          - 発送完了
6. buyer_received   - 購入者受取確認済み
7. completed        - 取引完了

### ステータス遷移図:

pending
   │
   │ propose_purchase_price (Seller)
   ↓
price_proposed
   │
   │ agree_purchase_price (Seller & Buyer両方)
   ↓
price_agreed
   │
   │ pay_for_purchase (Buyer)
   ↓
paid
   │
   │ save_shipping_info (Seller)
   ↓
shipped
   │
   │ confirm_buyer_received (Buyer)
   ↓
buyer_received
   │
   │ complete_purchase_trade (Seller)
   ↓
completed
   │
   │ アーカイブ処理
   ↓
archived_trades (アーカイブテーブルに移動)

### 逆方向の遷移（例外処理）:

- price_proposed → price_proposed: 金額の再提案（価格修正）
  ※ 金額修正時は合意フラグがリセットされる

- price_agreed → キャンセル不可
  ※ 合意後のキャンセルは禁止（ユーザーに警告表示）

4. 各ステップの詳細
================================================================================

┌──────────────────────────────────────────────────────────────┐
│ ステップ1: 金額提案（Seller → Buyer）                          │
└──────────────────────────────────────────────────────────────┘

役割: Seller（出品者）
画面: チャット画面

### UI表示条件:
- trade_type == 'exchange'
- status == 'pending' または 'price_proposed'
- 現在のユーザーがSeller

### ユーザー操作:
1. 「購入希望価格を提示する」ボタンをクリック
2. 金額入力モーダルが開く
3. 希望価格を入力
4. 手数料込みの総額が自動計算されて表示
   - Buyerの支払い総額 = 商品価格 + Stripe手数料(3.6%)
   - Sellerの受取金額 = 商品価格（100%）
5. 「提案する」ボタンをクリック

### API呼び出し:
POST /api/propose_purchase_price

Request:
{
  "trade_id": 123,
  "price": 5000,
  "message": "この価格でいかがでしょうか？" (任意)
}

Response:
{
  "success": true,
  "message": "金額を提案しました",
  "data": {
    "trade_id": 123,
    "purchase_price": 5000,
    "status": "price_proposed"
  }
}

### データベース変更:
UPDATE trades SET
  trade_type = 'purchase',
  purchase_price = 5000,
  price_proposed_by = <seller_id>,
  status = 'price_proposed',
  is_price_agreed_seller = FALSE,
  is_price_agreed_buyer = FALSE,
  updated_at = NOW()
WHERE trade_id = 123

### 画面遷移:
- 提案後、PriceAgreementコンポーネントが表示される
- 両ユーザーに「合意ボタン」が表示される

### 重要な仕様:
- 金額は何度でも修正可能（price_proposedステータスの間）
- 金額を修正すると、両者の合意フラグがリセットされる
- 最小金額: 1円
- 最大金額: 制限なし（実運用時は上限設定を検討）

┌──────────────────────────────────────────────────────────────┐
│ ステップ2: 金額合意（Seller & Buyer）                          │
└──────────────────────────────────────────────────────────────┘

役割: Seller & Buyer（両者）
画面: チャット画面

### UI表示条件:
- status == 'price_proposed'
- purchase_priceが設定されている

### ユーザー操作（Seller側）:
1. 提案された金額を確認
2. 「この金額で販売する」ボタンをクリック
3. 確認ダイアログ表示:
   「提案した金額 ¥5,000 で販売しますか？

   ⚠️ 注意: 金額に合意すると、取引をキャンセルすることができなくなります。」
4. OKをクリック

### ユーザー操作（Buyer側）:
1. 提案された金額を確認
2. 「この金額で購入する」ボタンをクリック
3. 確認ダイアログ表示:
   「¥5,000 で購入しますか？

   ⚠️ 注意: 金額に合意すると、取引をキャンセルすることができなくなります。」
4. OKをクリック

### API呼び出し:
POST /api/agree_purchase_price

Request (Seller):
{
  "trade_id": 123,
  "user_type": "seller"
}

Request (Buyer):
{
  "trade_id": 123,
  "user_type": "buyer"
}

Response:
{
  "success": true,
  "message": "金額に合意しました",
  "data": {
    "trade_id": 123,
    "status": "price_agreed",
    "both_agreed": true
  }
}

### データベース変更:

Sellerが合意:
UPDATE trades SET
  is_price_agreed_seller = TRUE,
  updated_at = NOW()
WHERE trade_id = 123

Buyerが合意:
UPDATE trades SET
  is_price_agreed_buyer = TRUE,
  updated_at = NOW()
WHERE trade_id = 123

両者が合意:
UPDATE trades SET
  status = 'price_agreed',
  updated_at = NOW()
WHERE trade_id = 123

### 画面遷移:
- 両者が合意すると、Buyerに「決済に進む」ボタンが表示
- Sellerには「Buyerの決済待ち」メッセージが表示

### 重要な仕様:
- 一方が合意しただけでは status は変わらない
- 両者が合意して初めて status が 'price_agreed' に変更
- 合意後のキャンセルは不可

┌──────────────────────────────────────────────────────────────┐
│ ステップ3: 決済実行（Buyer）                                   │
└──────────────────────────────────────────────────────────────┘

役割: Buyer（購入者）
画面: チャット画面 → 決済モーダル

### UI表示条件:
- status == 'price_agreed'
- 両者が合意済み
- 現在のユーザーがBuyer

### ユーザー操作:
1. 「決済に進む」ボタンをクリック
2. PaymentModalが開く
3. 金額詳細を確認:
   - 商品代金: ¥5,000
   - 決済手数料 (3.6%): ¥180
   - ─────────────────
   - 合計金額: ¥5,180
4. エスクロー説明を読む
5. 「¥5,180 を支払う」ボタンをクリック
6. 最終確認ダイアログ
7. OKをクリック

### API呼び出し:

Request:
{
  "trade_id": 123,
  "payment_method_id": "pm_test_success"  // Stripe決済方法ID
}

Response:
{
  "success": true,
  "message": "決済が完了しました",
  "data": {
    "trade_id": 123,
    "payment_intent_id": "pi_test_123_1732876800",
    "status": "paid"
  }
}

UPDATE trades SET

### エスクロー処理:
決済された金額は、Buyerが受取確認するまでプラットフォームで保管されます。
この時点では、Sellerへの支払いは確定していません。

### 画面遷移:
- 決済完了後、Sellerに「商品を発送する」ボタンが表示
- Buyerには「発送待ち」メッセージが表示

### 重要な仕様:
- 決済は一度のみ実行可能
- 決済失敗時は status は変更されない
- payment_intent_id は一意である必要がある

┌──────────────────────────────────────────────────────────────┐
│ ステップ4: 発送（Seller）                                      │
└──────────────────────────────────────────────────────────────┘

役割: Seller（出品者）
画面: チャット画面 → 発送情報入力モーダル

### UI表示条件:
- trade_type == 'purchase'
- status == 'paid'
- 現在のユーザーがSeller
- まだ発送情報が登録されていない

### ユーザー操作:
1. 「商品を発送する」ボタンをクリック
2. ShippingModalが開く
3. 発送情報を入力:
   - 配送会社（例: ヤマト運輸、佐川急便）
   - 追跡番号（例: 1234-5678-9012）
4. 「発送情報を送信」ボタンをクリック

### API呼び出し:
POST /api/saveShippingInfo

Request:
{
  "trade_id": 123,
  "sender_user_id": <seller_id>,
  "tracking_number": "1234-5678-9012",
  "shipping_company": "ヤマト運輸"
}

Response:
{
  "result": true,
  "message": "発送情報が保存されました"
}

### データベース変更:

shipping_info テーブルにINSERT:
INSERT INTO shipping_info (
  trade_id,
  sender_user_id,
  tracking_number,
  shipping_company,
  created_at
) VALUES (
  123,
  <seller_id>,
  '1234-5678-9012',
  'ヤマト運輸',
  NOW()
)

購入フローの場合、即座にステータス更新:
UPDATE trades SET
  status = 'shipped',
  updated_at = NOW()
WHERE trade_id = 123

### 画面遷移:
- 発送後、発送情報が両者に表示される
- Buyerに「商品を受け取りました」確認ボタンが表示
- Sellerには「Buyerの受取確認待ち」メッセージが表示

### 重要な仕様:
- 購入フローでは、Sellerのみが発送
- 発送情報登録と同時に status が 'shipped' に変更
- 発送情報は後から編集不可

DELETE FROM trade_messages WHERE trade_id = 123;
DELETE FROM shipping_info WHERE trade_id = 123;
DELETE FROM trades WHERE trade_id = 123;
DELETE FROM likes WHERE item_id = <item_id>;

│ Stripeへの支払い                                              │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│ エスクロー方式                                                │
└─────────────────────────────────────────────────────────────┘

決済時:
  Buyerの支払い(¥5,180) → プラットフォーム（エスクロー保管）

受取確認時:
  プラットフォーム → Sellerへ支払い(¥5,000)
  プラットフォーム → Stripeへ手数料支払い(¥180)

─────────┼─────────────┼─────────────┼─────────────
¥1,000   | ¥1,036      | ¥1,000      | ¥36
¥5,000   | ¥5,180      | ¥5,000      | ¥180
¥10,000  | ¥10,360     | ¥10,000     | ¥360
¥50,000  | ¥51,800     | ¥50,000     | ¥1,800

================================================================================
6. アーカイブ処理
================================================================================

### 目的:
取引完了後、取引データを永続的に保存し、アクティブなテーブルから削除することで、
データベースのパフォーマンスを維持します。

### 処理タイミング:
complete_purchase_trade APIが実行された時

### アーカイブされるデータ:

┌──────────────────────────────────────────────────────────────┐
│ 1. archived_trades（取引情報）                                 │
└──────────────────────────────────────────────────────────────┘

保存内容:
- original_trade_id: 元の取引ID
- trade_type: 'purchase'
- purchase_price: 購入金額
- payment_intent_id: Stripe決済ID
- paid_at: 決済日時
- buyer_received_at: 受取確認日時
- seller_id, buyer_id
- seller_name, buyer_name
- item_archive_id: アーカイブされた商品のID
- trade_created_at: 取引開始日時
- trade_completed_at: 取引完了日時

┌──────────────────────────────────────────────────────────────┐
│ 2. archived_items（商品情報）                                  │
└──────────────────────────────────────────────────────────────┘

保存内容:
- original_item_id: 元の商品ID
- title: 商品名
- description: 商品説明
- type: カテゴリ
- brand: ブランド
- user_id: 出品者ID
- owner_name_at_archive: アーカイブ時の所有者名

┌──────────────────────────────────────────────────────────────┐
│ 3. archived_item_images（商品画像）                            │
└──────────────────────────────────────────────────────────────┘

保存内容:
- archive_id: アーカイブされた商品ID
- original_item_image_id: 元の画像ID
- image_url: 画像URL
- image_order: 画像の順序

┌──────────────────────────────────────────────────────────────┐
│ 4. archived_trade_messages（メッセージ）                       │
└──────────────────────────────────────────────────────────────┘

保存内容:
- archive_trade_id: アーカイブされた取引ID
- original_message_id: 元のメッセージID
- sender_id: 送信者ID
- sender_name: 送信者名
- message: メッセージ内容
- sent_at: 送信日時

┌──────────────────────────────────────────────────────────────┐
│ 5. archived_shipping_info（発送情報）                          │
└──────────────────────────────────────────────────────────────┘

保存内容:
- archive_trade_id: アーカイブされた取引ID
- sender_user_id: 発送者ID
- sender_name: 発送者名
- tracking_number: 追跡番号
- shipping_company: 配送会社
- created_at: 発送日時

### アーカイブ後の削除:

以下のデータが元のテーブルから削除されます:
1. trade_messages (該当trade_idのメッセージすべて)
2. shipping_info (該当trade_idの発送情報)
3. trades (該当の取引レコード)
4. likes (該当item_idのいいね)
5. item_images (該当item_idの画像すべて)
6. items (購入された商品レコード)

10. セキュリティ考慮事項
================================================================================

### 1. 権限チェック:

各APIで適切なユーザーのみがアクセスできるようにする:
- 金額提案: Sellerのみ
- 決済: Buyerのみ
- 発送: Sellerのみ
- 受取確認: Buyerのみ
- 取引完了: Sellerのみ

### 2. ステータスチェック:

各操作は適切なステータスでのみ実行可能:
- 金額提案: pending, price_proposed
- 金額合意: price_proposed
- 決済: price_agreed
- 発送: paid
- 受取確認: shipped
- 取引完了: buyer_received

### 3. 金額改ざん防止:

- purchase_priceはバックエンドでのみ設定
- フロントエンドから送信された金額をそのまま信用しない
- 手数料計算はバックエンドで実施

### 4. エスクロー保護:

- 決済後、すぐにSellerに支払わない
- Buyerの受取確認後に支払いを確定
- 不正な受取確認を防ぐ仕組みが必要

### 5. Stripe決済セキュリティ:

- payment_intent_idの検証
- Webhook署名の検証
- 金額の再確認

### 6. SQLインジェクション対策:

- プレースホルダーを使用したクエリ実行
- ユーザー入力の直接埋め込みを禁止

### 7. XSS対策:

- ユーザー入力のエスケープ
- メッセージ表示時のサニタイズ
